# ADR-0001. Способ доставки кода на сервер

* Статус: принято
* Дата: 2026-10-05

## Контекст

TimeCapsule (Laravel, PHP 8.4, PostgreSQL 16) работает на одном сервере EC2 (t3.micro, Amazon Linux 2023)
в регионе eu-central-1. Код хранится в публичном репозитории GitHub `danielmihai-cloud/timecapsule`,
разработка ведётся на ноутбуке. Схема развёртывания: [`docs/architecture/deployment.drawio`](../architecture/deployment.drawio).

Нужно выбрать, как выпускать новые версии. Ограничения:

* сервер один, разработчик один, бюджет учебный, поэтому без отдельных сервисов CI/CD и платных инструментов;
* выпуск новой версии — это всегда одни и те же шаги: получить код, `composer install`,
  `php artisan migrate`, пересобрать кэш настроек, перезагрузить PHP-FPM;
* секреты (`.env` с паролем к базе) живут только на сервере и не должны попадать в репозиторий;
* `storage` и `bootstrap/cache` принадлежат пользователю `apache` (от него работает PHP-FPM),
  а код — пользователю `ec2-user`, поэтому команды `artisan` нужно запускать от `apache`;
* SSH (порт 22) открыт в Security Group только для IP разработчика, публичный IP сервера
  меняется после остановки экземпляра.

## Решение

Выпускаем новую версию скриптом `~/deploy.sh` на сервере, который запускается с ноутбука одной командой:

```bash
ssh -i ~/Downloads/danielmihai-keypair.pem ec2-user@<Public-IP> ./deploy.sh
```

Скрипт (`set -euo pipefail`, остановка на первой ошибке) выполняет по порядку:

1. `git pull --ff-only` — забирает код из GitHub по HTTPS, без ключей (репозиторий публичный);
2. `composer install --no-dev --optimize-autoloader --no-interaction --no-scripts`;
3. `sudo -u apache php artisan package:discover`, `migrate --force`, `config:cache`;
4. `sudo systemctl reload php-fpm`;
5. печатает коммит, который теперь работает на сервере.

Порядок выпуска: `git push` в GitHub → запуск `deploy.sh` по SSH.

## Рассмотренные альтернативы

* **Копирование файлов через `scp` (или `rsync`) с ноутбука.** Не нужен ни git на сервере, ни доступ
  к GitHub. Отказались: на сервер попадает то, что лежит на ноутбуке, включая незакоммиченные правки,
  поэтому нельзя сказать, какая версия работает; удалённые файлы `scp` не удаляет; `vendor` либо
  копируется целиком (долго), либо всё равно нужен `composer install` на сервере; откатиться не на что.
* **`git pull` и остальные команды вручную на сервере (вариант A).** Версия на сервере всегда равна
  коммиту, есть история и откат через git. Отказались как от основного способа: пять команд нужно
  каждый раз вводить руками, легко забыть `composer install` или миграции, а ошибку на середине
  можно не заметить. Остаётся запасным способом, если скрипт сломан.
* **Скрипт `deploy.sh`, запускаемый по SSH (выбрано).** Те же шаги, что и вручную, но всегда
  в одном порядке и одной командой; при ошибке выпуск останавливается и видно, на каком шаге.
* **CI/CD (GitHub Actions, AWS CodeDeploy).** Деплой сам запускался бы после `git push`.
  Отказались пока: нужно хранить SSH-ключ в секретах GitHub и открывать порт 22 для адресов GitHub
  либо настраивать CodeDeploy-агент и IAM-роли, а мы этого ещё не проходили.
  Скрипт `deploy.sh` можно будет без изменений вызывать из такого пайплайна.
* **Приватный репозиторий с deploy key.** Код был бы закрыт, но на сервере пришлось бы хранить
  ещё один ключ. В коде нет секретов, поэтому репозиторий сделали публичным.

## Последствия

* Плюс: выпуск — одна команда с ноутбука, без входа на сервер; шаги не пропускаются и всегда идут
  в одном порядке.
* Плюс: на сервере всегда известный коммит (последняя строка вывода), откат — `git revert` плохого
  коммита на ноутбуке, `git push` и повторный запуск `deploy.sh`.
* Плюс: сервер может только читать репозиторий; даже при взломе сервера код в GitHub не изменить.
* Плюс: `git pull --ff-only` откажется работать, если на сервере правили файлы руками,
  а не смешает правки с новым кодом.
* Минус: во время `git pull` и `composer install` (несколько секунд) на сервере лежит смесь старой
  и новой версии, посетитель может получить ошибку 500. Нет режима обслуживания и атомарного
  переключения (например, через симлинк на папку релиза).
* Минус: деплой запускается вручную, его можно забыть сделать после `git push`.
* Риск: публичный IP меняется после остановки экземпляра, а SSH открыт только для одного IP —
  перед деплоем нужно сверять адрес сервера и правило Security Group (решается Elastic IP).
* Риск: миграции выполняются сразу на рабочей базе без резервной копии; неудачную миграцию
  придётся исправлять вручную.
* Риск: если GitHub недоступен, выпустить новую версию нельзя (уже работающий сайт это не затрагивает).
