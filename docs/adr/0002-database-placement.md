# ADR-0002. Где размещать базу данных

* Статус: принято
* Дата: 2026-11-01

## Контекст

В ЛР2 TimeCapsule (Laravel 12, PHP 8.4, PostgreSQL 16) работала на одном экземпляре EC2 в default VPC:
nginx, PHP-FPM и PostgreSQL на одном сервере в публичной подсети, база слушала `127.0.0.1`
(решение о деплое — [ADR-0001](0001-deploy-method.md)).

В ЛР3 построена своя сеть `timecapsule-dev-vpc` (`10.7.0.0/16`): две зоны доступности, публичные подсети
`public-a`/`public-b` с маршрутом в Internet Gateway, приватные `private-a`/`private-b` без выхода в интернет,
отдельный `bastion` для SSH. Схема: [`docs/architecture/network-lab3.drawio`](../architecture/network-lab3.drawio).

Нужно решить, где будет жить база. Ограничения:

* в базе почта пользователей, хэши паролей и капсулы: она не должна быть доступна из интернета,
  даже если ошибиться в одной настройке;
* приложение должно находить базу по имени, которое переживёт пересоздание сервера базы;
* бюджет учебный: никаких постоянных почасовых платежей за то, что нужно раз в месяц
  (NAT Gateway в eu-central-1 — $0,052 в час, около $1,25 в сутки);
* базе всё равно нужны обновления безопасности из репозиториев Amazon Linux 2023;
* разработчик один, администрирование по SSH.

## Решение

База живёт на отдельном экземпляре `timecapsule-dev-db` (PostgreSQL 16, t3.micro) в приватной подсети
`timecapsule-dev-private-a` (`10.7.10.0/24`):

1. У сервера нет публичного адреса, а в `timecapsule-dev-private-rt` нет маршрута `0.0.0.0/0`
   (кроме времени обновления пакетов).
2. `timecapsule-dev-db-sg` пускает PostgreSQL 5432 только от группы `timecapsule-dev-web-sg`,
   SSH 22 — только от `timecapsule-dev-bastion-sg`.
3. `pg_hba.conf` пускает только пользователя `timecapsule` в базу `timecapsule` из `10.7.0.0/24`
   по паролю (`scram-sha-256`); пароль новый, сгенерирован случайно.
4. Приложение обращается к базе по имени `db.timecapsule.internal` (приватная зона Route 53
   `timecapsule.internal`, связанная только с этой VPC, TTL 60 с).
5. Пакеты обновляются через временный NAT Gateway: `scripts/nat-up.sh` → `sudo dnf -y update` →
   `scripts/nat-down.sh`.

## Рассмотренные альтернативы

* **На одном сервере с приложением, как в ЛР2.** Проще и дешевле всего: один сервер, база на `127.0.0.1`,
  минимальная задержка, порт 5432 наружу не открыт. Отказались: сервер стоит в публичной подсети с публичным
  адресом, и взлом веб-приложения (уязвимость в PHP-коде) сразу даёт доступ к файлам базы; приложение и база
  делят 1 ГБ памяти t3.micro; второй сервер приложения поднять нельзя — у каждого была бы своя база;
  `Terminate` экземпляра уничтожает и данные.
* **Отдельный сервер в публичной подсети.** Ресурсы разделены, обновления скачиваются напрямую через
  Internet Gateway, NAT не нужен. Отказались: у базы публичный адрес и маршрут в интернет, от интернета её
  защищают только Security Group и `pg_hba.conf`. Одна ошибка (правило 5432 ← `0.0.0.0/0` «для проверки»)
  открывает порт ботам, которые постоянно сканируют 5432 во всех публичных диапазонах AWS.
* **Отдельный сервер в приватной подсети (выбрано).** Три независимых барьера: нет адреса и маршрута,
  `db-sg`, `pg_hba.conf`. Чтобы база стала доступна из интернета, нужно ошибиться минимум в двух местах сразу.
  Цена — обновления только через временный NAT и SSH только через bastion.
* **Amazon RDS for PostgreSQL в приватных подсетях.** Обновления, резервные копии и Multi-AZ берёт на себя AWS.
  Отказались пока: RDS ещё не проходили, это отдельная почасовая плата за экземпляр базы и хранилище,
  а лабораторная требует собственный `db-server`. Это естественный следующий шаг, когда понадобится
  отказоустойчивость (см. «Последствия»).

## Последствия

* Плюс: база недоступна из интернета. Проверено в ЛР3: с `bastion` порт 5432 `closed`, с `web-server`
  `open`; с `db-server` запрос к `https://github.com` обрывается по таймауту.
* Плюс: приложение не знает IP базы. Если `db-server` пересоздадут, меняется одна запись `db` в Route 53,
  `.env` на `app-server` не трогаем.
* Плюс: веб-слой можно масштабировать: несколько `app-server` в разных зонах подключаются к одной базе.
* **Обновления без постоянного выхода в интернет.** У `db-server` нет постоянного пути наружу. Когда нужны
  обновления, `scripts/nat-up.sh` выделяет Elastic IP, создаёт NAT Gateway `timecapsule-dev-nat-a` в `public-a`
  и добавляет маршрут `0.0.0.0/0` в `private-rt`; после `sudo dnf -y update` скрипт `scripts/nat-down.sh`
  удаляет маршрут, шлюз и освобождает адрес. Стоимость: NAT Gateway — $0,052 в час плюс плата за каждый
  обработанный гигабайт, публичный IPv4 — $0,005 в час. Сеанс обновления на 15–20 минут стоит центы;
  постоянный NAT стоил бы около $1,25 в сутки (≈ $38 в месяц) — дороже всей остальной сети вместе.
  Обратная сторона — ручная процедура, о которой можно забыть (тогда база не получает исправлений), и риск
  забыть `nat-down.sh` (тогда растёт счёт; поэтому скрипт напоминает об этом, а ID сохраняются в файл,
  чтобы удалить ресурсы даже после сбоя). Возможное улучшение: репозитории Amazon Linux 2023 лежат в S3
  (это видно по адресам `al2023-repos-eu-central-1-…s3…amazonaws.com` в ошибке `dnf`), поэтому бесплатный
  шлюзовой VPC endpoint для S3 в `private-rt` дал бы `dnf` доступ к репозиториям без NAT. Сначала это нужно
  проверить.
* **Elastic IP у `app-server`.** У сервера приложения постоянный адрес `timecapsule-dev-app-eip`
  (`3.64.208.134`): `APP_URL` в `.env` и адрес в браузере не меняются после Stop/Start. Elastic IP стоит
  $0,005 в час всегда, даже у остановленного сервера. Bastion он не нужен: к bastion подключается только
  администратор, и новый адрес достаточно вписать в `~/.ssh/config`. **Когда перед приложением появится
  балансировщик нагрузки** (ALB), точкой входа станет DNS-имя балансировщика (его IP меняются, Elastic IP
  к ALB не привязывают). Серверы приложения переедут в приватные подсети за балансировщик, их Elastic IP
  можно будет освободить, `web-sg` будет пускать 80 только от Security Group балансировщика, а `APP_URL`
  станет доменом с alias-записью Route 53 на ALB. Исходящий трафик серверов (`git pull`, `composer`) тогда
  пойдёт через NAT или VPC endpoints.
* Минус: администрирование сложнее — SSH только через bastion (`ProxyJump`), публичный адрес bastion
  меняется после каждого запуска.
* Минус: база — единая точка отказа, и `db-server`, и `app-server` стоят в одной зоне `eu-central-1a`.
  При остановленном `db-server` приложение отвечает 500 (`/health` — через ~30 с ожидания соединения,
  проверено в ЛР3). Для отказоустойчивости нужны реплика в `private-b` или RDS Multi-AZ.
* Риск: автоматических резервных копий базы нет — нужно добавить снапшоты EBS по расписанию или `pg_dump`
  в S3 (у RDS это встроено).
* Риск: пароль базы лежит в `.env` на `app-server` (права 640, `ec2-user:apache`). Кто получит доступ к
  `app-server`, получит и доступ к базе — поэтому в `pg_hba.conf` разрешены только один пользователь и
  одна база.
