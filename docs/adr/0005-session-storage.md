# ADR-0005. Где хранить сессии пользователей

* Статус: принято
* Дата: 2026-11-10

## Контекст

До ЛР6 TimeCapsule работал на одном сервере `app-server` (Elastic IP `3.64.208.134`). Laravel хранил сессии
драйвером `file` в каталоге `storage/framework/sessions` на диске сервера. Вложения уже лежат в S3
([ADR-0003](0003-attachment-storage.md)), данные — в RDS ([ADR-0004](0004-database-hosting.md)), так что сессии
остались единственным состоянием, привязанным к конкретному серверу.

В ЛР6 приложение работает в группе Auto Scaling `timecapsule-dev-asg` из 2–4 одинаковых серверов в двух зонах
за Application Load Balancer `timecapsule-dev-alb`. Балансировщик распределяет запросы между исправными серверами
по кругу (round robin), а группа сама добавляет серверы под нагрузкой, удаляет лишние и заменяет неисправные.
С файловыми сессиями пользователь, вошедший на одном сервере, на следующем запросе к другому серверу оказывается
не залогинен, а при удалении сервера его сессии пропадают.

Ограничения:

* вход должен сохраняться, на какой бы сервер ни попал запрос и сколько бы серверов ни добавила или ни убрала
  группа;
* любой сервер можно удалить в любой момент без потери данных пользователей;
* никаких ключей доступа на серверах: только временные учётные данные роли `timecapsule-dev-app-role`, как в ЛР4;
* минимум изменений в коде: Laravel 12 уже умеет хранить сессии в кэше, базе и DynamoDB;
* учебный бюджет: сессий немного, нагрузка появляется только во время проверок;
* сессии живут `SESSION_LIFETIME` = 120 минут и после этого никому не нужны.

## Решение

Сессии хранятся в таблице Amazon DynamoDB `timecapsule-dev-sessions`:

1. Таблица в режиме `On-demand`, ключ раздела `key` (String), TTL по атрибуту `expires_at`. Одна сессия —
   один элемент: ключ — префикс кэша и идентификатор сессии из cookie, значение — сериализованные данные сессии,
   `expires_at` — время истечения в секундах Unix.
2. В `config/cache.php` добавлено хранилище `dynamodb` (таблица из `DYNAMODB_CACHE_TABLE`, регион из
   `AWS_REGION`, без ключей доступа). В `.env` на серверах `SESSION_DRIVER=dynamodb` и
   `DYNAMODB_CACHE_TABLE=timecapsule-dev-sessions`.
3. AWS SDK берёт учётные данные роли экземпляра. Политика `timecapsule-dev-app-sessions` разрешает этой роли
   только `GetItem`, `PutItem`, `UpdateItem` и `DeleteItem` и только для этой таблицы.
4. Привязка сессий (stickiness) в целевой группе `timecapsule-dev-tg` выключена: любой запрос может попасть на
   любой исправный сервер.

## Рассмотренные альтернативы

* **Сессии на сервере и привязка сессий в балансировщике (sticky sessions).** ALB ставит cookie `AWSALB` и
  отправляет запросы одного браузера на тот же сервер, пока жив cookie (по умолчанию сутки). Кода менять не
  нужно, нового сервиса нет, сессии читаются с локального диска без сетевых задержек. Отказались: привязка не
  убирает состояние с сервера, а только маскирует проблему. Когда группа удаляет сервер при уменьшении нагрузки
  или заменяет неисправный по проверке ELB, все его пользователи теряют вход; то же при отказе зоны и при замене
  серверов новым образом. Нагрузка распределяется неравномерно: пользователи «прилипают» к старым серверам, а
  новые, запущенные под нагрузкой, получают только новых посетителей, поэтому target tracking помогает хуже.
* **Таблица сессий в RDS (драйвер `database`).** Сервис уже есть, сессии хранятся транзакционно рядом с
  данными и ничего не стоят сверх базы. Отказались: нужна новая миграция с таблицей `sessions` (в TimeCapsule её
  нет), а главное — Laravel читает и перезаписывает сессию на каждом запросе, так что каждая страница добавляет
  единственной базе `db.t4g.micro` чтение и запись. Сессии наследуют все слабые места базы: она Single-AZ, по
  ночам останавливается расписанием, при её перезагрузке или отказе зоны `eu-central-1a` пропадает и вход.
  Просроченные строки удаляет сборщик мусора Laravel (лотерея 2 из 100 запросов), то есть ещё запросы `DELETE` к
  той же базе.
* **Таблица DynamoDB (выбрано).** Серверов у DynamoDB нет: данные таблицы AWS сам хранит в нескольких зонах
  региона, пропускная способность в режиме `On-demand` подстраивается под запросы, платим только за запросы и
  объём. Драйвер есть в Laravel из коробки, доступ даёт IAM-роль, старые сессии бесплатно удаляет TTL. Цена:
  каждый запрос к приложению — один `GetItem` и один `PutItem` по сети (миллисекунды внутри региона), чтение
  в драйвере Laravel только «в конечном счёте согласованное» (`ConsistentRead=false`), а приложение зависит от
  ещё одного регионального сервиса.

## Последствия

* **Вход не зависит от сервера.** Cookie браузера по-прежнему содержит только идентификатор сессии, а данные
  любой сервер читает из таблицы. Пользователь остаётся залогиненным при переходе между серверами, при росте
  группы с 2 до 4 серверов и при её сокращении (проверено в заданиях 5 и 6). Сервер можно удалить в любой момент:
  на его диске нет ничего, что нужно пользователям, поэтому серверы взаимозаменяемы и создаются из одного образа.
* **Стоимость.** Сессия занимает меньше 1 КБ, поэтому запись — 1 единица записи, чтение — 0,5 единицы чтения.
  В режиме `On-demand` после снижения цен в ноябре 2024 года это $0,625 за миллион единиц записи и $0,125 за
  миллион единиц чтения в us-east-1 (в eu-central-1 немного дороже), то есть меньше доллара за миллион
  просмотров страниц. Удаление по TTL бесплатное, хранение — центы. Для учебного проекта расход — доли цента за
  занятие; простаивающая таблица почти ничего не стоит, поэтому её не удаляют между занятиями.
* **Срок жизни.** Laravel записывает в `expires_at` время истечения (120 минут после последнего запроса) и не
  принимает просроченную сессию, даже если элемент ещё в таблице. TTL удаляет такие элементы в фоне, обычно в
  течение нескольких дней, без расхода единиц записи.
* **Согласованность.** Драйвер Laravel читает сессию без строгой согласованности: если два запроса одного
  пользователя почти одновременно уйдут на разные серверы, второй может прочитать сессию до записи первого.
  Для входа и формы создания капсулы это безопасно (худший случай — повторный вход или повтор формы из-за
  CSRF-токена), но хранить в сессии счётчики или корзину с частыми изменениями так нельзя.
* **Безопасность.** Политика разрешает четыре операции над одним ресурсом; читать или удалять другие таблицы
  роль не может. В таблице лежат данные сессий (идентификатор пользователя и CSRF-токен), поэтому значения
  элементов и cookie в отчёт не попадают. Шифрование таблицы — ключом, которым владеет AWS.
* **Сеть.** Серверы обращаются к DynamoDB по HTTPS через Internet Gateway, как к S3. Если серверы когда-нибудь
  переедут в приватные подсети, понадобится шлюзовая конечная точка VPC для DynamoDB (бесплатная).
* **Переход.** Файловые сессии на `app-server` не переносились: после выпуска версии с DynamoDB все
  пользователи один раз вошли заново. Образ `timecapsule-dev-app-lab6` снят уже после этого, поэтому
  `SESSION_DRIVER=dynamodb` есть у каждого сервера группы.
* **Минус:** приложение теперь зависит от DynamoDB в `eu-central-1`. При недоступности сервиса пользователи не
  смогут войти и пользоваться сессией, хотя серверы и база будут работать.
