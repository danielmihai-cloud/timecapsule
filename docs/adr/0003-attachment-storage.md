# ADR-0003. Где хранить вложения пользователей

* Статус: принято
* Дата: 2026-11-08

## Контекст

К капсуле TimeCapsule можно прикрепить файл: картинку (JPEG, PNG, GIF, WebP) или PDF до 5 МБ. До ЛР4 модуль
хранения `app/Services/CapsuleStorage.php` сохранял файлы в папку `storage/uploads` на корневом диске EBS
`app-server` (`timecapsule-dev-app` в `public-a`), а `CapsuleController::file()` отдавал их браузеру через
PHP. Остальные данные уже вынесены с сервера: база — на `db-server` в приватной подсети
([ADR-0002](0002-database-placement.md)), код — в GitHub ([ADR-0001](0001-deploy-method.md)).

Вложения остались единственным состоянием на `app-server`. Из-за этого:

* сервер нельзя заменить новым или пересоздать из образа: файлы есть только на его диске, а у корневого
  тома включено `Delete on termination`;
* нельзя запустить второй сервер приложения: каждый видел бы только свои файлы;
* каждое скачивание вложения проходит через PHP-FPM и занимает процесс на всё время передачи.

Ограничения:

* вложения приватные: капсулу видит только её владелец, а публичную после открытия — все; файл запечатанной
  капсулы не отдаётся никому, даже владельцу; правила проверяет приложение;
* случайное или злонамеренное удаление не должно уничтожать файлы безвозвратно;
* стоимость должна расти только вместе с объёмом данных и не требовать постоянных почасовых платежей;
* приложение не должно хранить долгоживущие ключи доступа (репозиторий публичный).

## Решение

Вложения хранятся в бакете Amazon S3 `timecapsule-dev-uploads-danielmihai` (регион `eu-central-1`) под
префиксом `uploads/`:

1. **Бакет закрыт:** Block all public access, ACL выключены (Bucket owner enforced), шифрование SSE-S3,
   политика бакета запрещает (`Deny`) любые запросы не по HTTPS (`aws:SecureTransport = false`).
2. **Версионирование включено**, правило жизненного цикла `timecapsule-dev-noncurrent` (только `uploads/`):
   неактуальные версии через 30 дней переходят в Standard-IA, через 90 дней удаляются (кроме двух самых
   новых), незавершённые загрузки частями удаляются через 7 дней.
3. **Права приложения** — роль `timecapsule-dev-app-role` с политикой `timecapsule-dev-app-s3`:
   `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` только на `uploads/*`. Нет `s3:DeleteObjectVersion`,
   `s3:PutBucketPolicy`, `s3:PutBucketVersioning`, `s3:PutLifecycleConfiguration`. Роль привязана к
   `app-server` через профиль экземпляра; в `.env` только `S3_BUCKET` и `AWS_REGION`, ключей нет.
4. **Модуль хранения** работает только с S3 через AWS SDK for PHP: `save()` → `PutObject` под ключом
   `uploads/<случайное имя>` с правильным `ContentType`, `delete()` → `DeleteObject`, `stream()` →
   ответ 302 на подписанный URL `GetObject` сроком 5 минут с `ResponseContentType` и
   `ResponseContentDisposition` (inline для картинок, attachment с исходным именем для PDF).
5. Существующие файлы ЛР2/ЛР3 перенесены командой `aws s3 sync`, папка `storage/uploads` на сервере удалена.

## Рассмотренные альтернативы

* **Диск EBS сервера приложения (как было).** Ничего не нужно менять, задержка минимальная, gp3 стоит
  $0,0952 за ГБ-месяц. Отказались: том подключается только к одному экземпляру в одной зоне доступности
  (Multi-Attach есть только у io1/io2 и требует кластерной файловой системы), поэтому второй сервер и
  балансировщик невозможны. Файлы пропадают вместе с сервером, место выделяется заранее и оплачивается целиком,
  резервные копии — только снапшоты всего диска, а отдача файлов нагружает PHP.
* **Общая файловая система Amazon EFS.** Монтируется по NFS на несколько серверов в разных зонах, код
  модуля почти не меняется (тот же `local`-диск, только папка на EFS). Отказались: нужны mount target
  в каждой подсети, Security Group для NFS 2049 и `amazon-efs-utils` на каждом сервере; хранение заметно
  дороже — Standard около $0,30 за ГБ-месяц (в us-east-1, во Франкфурте дороже) против $0,0245 у S3 Standard;
  файлы по-прежнему отдаёт PHP; нет версионирования объектов и подписанных ссылок, защита от удаления —
  только AWS Backup.
* **Бакет Amazon S3 (выбрано).** Хранилище не привязано ни к серверу, ни к зоне (S3 Standard хранит данные
  минимум в трёх зонах региона), платим за фактический объём ($0,0245 за ГБ-месяц в `eu-central-1`) и запросы,
  есть версионирование и правила жизненного цикла, доступ описывается IAM-политиками. Браузер скачивает файл
  напрямую из S3 по подписанной ссылке, минуя сервер. Цена — модуль хранения переписан под AWS SDK, а для
  разработки нужна роль или ключи (локально без AWS модуль не работает).

## Последствия

* **Как пользователь получает файл.** Браузер запрашивает `GET /capsules/{id}/file`. Laravel проверяет
  права пользователя на капсулу (видна ли она ему и открыта ли) и только потом подписывает ссылку
  `GetObject` для `uploads/<имя>` и отвечает 302. Подпись вычисляется локально временными ключами роли,
  запроса к S3 при этом нет. Браузер скачивает файл из
  `https://timecapsule-dev-uploads-danielmihai.s3.eu-central-1.amazonaws.com/uploads/...` с параметрами
  `X-Amz-*`. S3 проверяет подпись, срок и права роли на `uploads/*`, а заголовки `Content-Type` и
  `Content-Disposition` берёт из подписанных параметров `response-*`. Срок ссылки ограничивают
  `X-Amz-Expires=300` (5 минут, задаётся в коде) и срок действия временных ключей роли, которыми она
  подписана: ссылка перестаёт работать, когда истечёт любой из них. Ссылку нельзя изменить (другой ключ,
  другой метод — `SignatureDoesNotMatch`), а после срока S3 отвечает `AccessDenied: Request has expired`,
  поэтому пересланную ссылку не нужно отзывать.
* **Что защищает от случайного удаления.** Версионирование: `DeleteObject` без идентификатора версии только
  ставит маркер удаления, а перезапись создаёт новую версию. Окончательно удалить версию может только тот,
  у кого есть `s3:DeleteObjectVersion`, а у приложения его нет — даже с украденными ключами роли файлы
  не уничтожить сразу. Политика бакета и Block Public Access защищают от утечки, а не от удаления.
  Слабое место — правило жизненного цикла: если перезаписать файл трижды, исходная версия перестаёт быть
  одной из двух самых новых неактуальных и через 90 дней удаляется. Для критичных данных нужен S3 Object
  Lock или репликация в другой бакет.
* **Что ограничивает рост стоимости.** Правило `timecapsule-dev-noncurrent`: старые версии через 30 дней
  переходят в Standard-IA ($0,0135 за ГБ-месяц, только объекты от 128 КБ), через 90 дней удаляются, кроме
  двух самых новых; незавершённые загрузки частями удаляются через 7 дней. Размер вложения ограничен
  приложением (5 МБ), трафик скачивания идёт напрямую из S3 и не нагружает сервер. Ограничение: у файла
  удалённой капсулы остаётся ровно одна неактуальная версия, а правило хранит две самые новые, поэтому она
  не удалится сама. Чтобы через 90 дней исчезали и такие файлы, нужно второе правило без
  `NewerNoncurrentVersions` или периодическая очистка.
* **Когда серверов станет несколько и появится балансировщик.** Модуль хранения менять не нужно: все
  экземпляры Auto Scaling Group получают ту же роль через launch template и видят один и тот же бакет, сессии
  при этом нужно вынести из `storage/framework/sessions` (база или Redis). Сервер можно заменить в любой
  момент: на нём только код и `.env`. Балансировщик пропускает через себя только запрос к приложению
  (302), сам файл идёт мимо него и мимо серверов. Серверы приложения уйдут в приватные подсети, и к S3 они
  будут ходить через шлюзовой VPC endpoint для S3 (бесплатно, без NAT); тогда в политику бакета можно добавить
  условие `aws:SourceVpce`, а для раздачи большого трафика — CloudFront с OAC.
* Минус: локальная разработка без доступа к AWS больше не работает — нужен бакет и роль (или MinIO и
  отдельная конфигурация). Ключи доступа IAM для этого не создаём.
* Минус: появились новые точки отказа и расходы — недоступность S3 в регионе означает недоступность
  вложений; для отказа региона понадобится репликация бакета в другой регион (CRR).
